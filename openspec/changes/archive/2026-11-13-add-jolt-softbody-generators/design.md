Existing AuroraCook.Static links Aurora.Adaptor.Static. A new builder must not acquire that dependency by linking the large cook library. Instead the existing Aurora cook module implements the consumer-owned IMeshAuthoringCompiler contract from Physics.SoftBody.Interface, supplying source extraction and owned product construction. No second importer and no duplicate compilation of existing mesh cpp files are introduced. Mesh document passes generic source/revision context and delegates generator-specific control editing through registered editor interfaces, rather than constructing SoftBody plugin data.

The compiler registry protects an owned shared service pointer with an instance mutex so a worker acquires ownership through completion; a borrowed generic interface pointer would not provide that lifetime. Removal verifies both pointer and shared ownership identity, and retires the provider outside the lock. This replaces the initial atomic shared-pointer specialization, unavailable in the selected Android NDK libc++. This is an offline compiler service, outside the runtime solver path. Init registers one provider, Shutdown removes that exact provider, and duplicate/foreign registrations fail. SoftBody.Editor implements the mesh protocol defined by its consumer in the existing Aurora editor foundation target; Aurora has no SoftBody plugin dependency.

## D2 CPU solver and physics collision contract

The user approved the independent CPU XPBD recommendation on 2026-11-02 after requiring Android, iOS and OHOS. Each SoftBody component owns a solver instance and a UUID identity, distinct from backend PhysicsObjectId handles. Descriptors contain particles, mass/constraint mode, unique edges, oriented positive-volume tets, outer faces, material parameters and initial pose. Snapshots own their positions/velocities; no JPH or backend actor pointer crosses the interface.

The existing fixed-step owner still performs one rigid-world update. Before that update, the component validates/samples its root target; after completion it advances CPU XPBD once against the completed rigid step's collision provider. `solverIterations` repeats projections at the same step size, with multipliers cleared once per fixed step and accumulated within those iterations. It does not divide the tick into native Jolt Small Steps. Physics pause/single-step and completed-sample interpolation remain shared with the host. Closing the world invalidates borrowed collision services and removes the pose contribution.

Predict positions from velocity and world gravity, then project edges, tetrahedral volumes, dynamic root-follow targets and sphere contacts in each iteration. Only vertices referenced by outer surface faces query contacts; internal controls still participate in deformation and following, matching the reference's non-colliding center point. Reconstruct velocity from final displacement and apply time-based damping plus relative contact friction/restitution. Inversion, nonfinite state, unsupported contacts or unresolved final penetration return explicit failures and preserve the previous complete solver state. Root reset rebuilds rest positions at the requested transform and clears velocity. Nonzero gas pressure is explicitly unsupported by the initial CPU solver; volume compliance controls tetrahedral volume preservation.

Control modes are Dynamic with positive inverse mass, WorldFixed with zero inverse mass, and optional RootKinematic points placed at root-relative targets. The seal defaults to a configurable budget of 30 physical control points plus an identity root bone. All example points are dynamic and follow `rootTarget * restPosition` through positive finite-compliance XPBD constraints. Pins are optional and do not substitute for compliant following.

`ISoftBodyCollisionQuery` is owned by the consuming Physics softbody domain and exposed optionally by IPhysicsWorld. A query carries the completed step number, its full delta time, a point trajectory, radius and two-sided collision filter. The provider returns all required sphere sweep and penetration contacts, with stable rigid-object/feature identities, outward normals, step-end contact planes, surface velocities and TOI fractions. Failure preserves the caller's previous output. Queries for stale time intervals fail. Translating kinematic obstacles use the complete rigid-step trajectory; unsupported rotating obstacle motion fails explicitly rather than masquerading as end-pose CCD.

External rigid contacts are one-way against static and translating kinematic obstacles, matching the reference scope. Dynamic rigid reaction remains explicitly unsupported. The user subsequently requested bilateral soft-soft tests; the batch extension below supplies that interaction independently of the Jolt rigid query provider. The Jolt provider does not allocate helper particles or native softbody actors, and CPU instances are never passed to rigid-body APIs. No root-follow patch or extra Jolt update remains. High-resolution visible skin does not imply equally detailed collision geometry.

The reference additionally modulates center follow compliance and relative velocity damping near contacts. The initial uniform-compliance implementation does not claim that extra controller. Parameter units are meters/seconds/kg; reference values expressed in centimetres require dimensional conversion.

### Mobile and future PhysX review (2026-11-02)

The user now requires Android and iOS and added "oho", interpreted as OHOS/OpenHarmony. Runtime softbody simulation must have a CPU path with no CUDA dependency. Editor generation and cooking remain offline operations. A Windows build or an ARM64-compatible algorithm is not mobile acceptance; platform builds and real device timing/thermal checks remain outstanding.

The initial mobile acceptance target is 60 FPS with ten animals, selected by the user. Each example defaults to thirty configurable dynamic controls and at most four influences per visible vertex. Lowest device models and CPU/GPU frame budgets have not yet been supplied, and the target is not a measured performance result.

PhysX provides FEM deformable volumes, separate simulation/collision tetrahedral meshes, Tet Maker and volume embedding/skinning. Its volume implementation is GPU-only and requires CUDA: see the [5.7 overview](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/DeformableBodyOverview.html), [volume documentation](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/DeformableVolume.html) and [current native header](https://github.com/NVIDIA-Omniverse/PhysX/blob/main/physx/include/PxDeformableVolume.h). This restriction does not mean CPU PhysX rigid bodies require CUDA. Public PhysX build presets currently cover Windows/Linux; Android/iOS rely on community port evaluation, and OHOS support has not been established ([presets](https://github.com/NVIDIA-Omniverse/PhysX/tree/main/physx/buildtools/presets/public), [maintainer discussion](https://github.com/NVIDIA-Omniverse/PhysX/discussions/58)).

The selected route is one portable CPU XPBD solver consuming a Physics-owned collision interface, with Jolt initially providing queries and a future PhysX provider implementing the same contract. Generator, source identities, four-weight skinning and pose-owner boundaries are reused. A future PhysX provider is an interface extension point, not a claim that a mobile PhysX backend has already been ported or verified.

The reference project's `Agent/Temp/UE58_JellyMonster_Implementation_Plan.md` explicitly identifies mobile CPU low-resolution XPBD as its goal (line 62), says PhysX is not integrated (line 90), and requires engine-independent arrays/math so migration replaces only collision and skeletal adapters (line 132). Its first scope accepts one-way shell contacts (line 104). These are documented reasons for the architecture; no comparative PhysX performance result was found.

The lifecycle/snapshot layer may be shared with a future native FEM provider, but XPBD compliance and gas pressure must not be presented as direct aliases for PhysX Young's modulus and Poisson's ratio. Capabilities must separately describe compliant following, pinning, soft-soft/rigid interaction, CPU/GPU execution and data synchronization. A deformable attachment or kinematic target is not automatically equivalent to the reference's finite-compliance root following. PhysX-specific cooking data and device buffers remain backend-owned.

## D3 Binding generator

Inputs: owned source geometry/material/attribute snapshot with revision; mandatory control points with stable IDs and positions; WorldFixed/RootKinematic constraints; control budget; resolution/quality settings and deterministic algorithm revision. The default AutoFit volume profile requires a closed, consistently oriented, nondegenerate connected star-shaped shell. AutoFit verifies a nonempty visibility kernel (or verifies the authored center); a closed concave mesh without a valid kernel is explicitly unsupported by that mode. Detached face accessories are separate render parts with an explicit attachment policy.

The conservative occupied-cell lattice prototype demonstrated conforming subdivision and four-weight coverage, but failed the seal's collision-proxy quality test at the current bone budget: 254 points still enclosed 2.666 times the body's volume with a sampled maximum external gap of 17.65 cm. It is not the accepted production default. Production generation requires a boundary-fitted or adaptive proxy and explicit surface-distance/volume diagnostics before acceptance; a valid embedding alone does not demonstrate acceptable collision fidelity.

Production evaluates two bounded cage candidates around the same verified center. The existing `adaptive-star-cage-v1` profile adaptively bisects spherical edges, clips full source triangles against each cone, and fits radial boundary vertices. The `adaptive-support-cage-v2` profile starts from six axis-aligned source support planes, then greedily clips the convex boundary with supporting planes from a deterministic 642-direction icosphere pool. Candidate normals account for source bounding-box dimensions; clipping operates in normalized coordinates. Each supporting plane uses the maximum source projection plus a safety margin of the source bounding-box diagonal times 1e-7. Shared edges reuse their intersection vertices, and polygon triangulation retains collinear boundary vertices while checking winding and closure. A proposed cut is eligible only within the remaining shell-vertex budget; the eligible cut with the greatest volume reduction is selected deterministically. The support profile does not run a second importer or add a meshing dependency, module or target.

Both candidates use the same source geometry, authored center and mandatory controls. Each boundary triangle forms a tetrahedron with the center. After conversion to the stored position precision, both pass the same completion chain: exact mandatory-point insertion, positive-volume and minimum-quality checks, manifold boundary checks, full source-triangle coverage, surface-distance certification, four-weight binding and descriptor validation. Only complete valid candidates compete; the one with smaller cage volume is published, retaining the star candidate on an equal-volume tie. An invalid support candidate cannot replace a valid star candidate, and failure of both or cancellation preserves the previous output. The convex support candidate may fill concavities; the shared quality gates and competing star profile remain necessary. This does not broaden the accepted source class beyond the verified connected star-shaped shell.

Distance diagnostics measure the maximum, over the complete cage boundary, of nearest distance to the source display surface. `maximumSampledSurfaceDistance` records evaluated cage corners and subdivision centroids; `maximumSurfaceDistance` is the certified upper bound obtained from each subtriangle's centroid distance plus its maximum centroid-to-vertex radius, using the distance function's 1-Lipschitz property. Refinement requires the bound to satisfy the configured tolerance and approach the measured maximum within `min(sourceDiagonal * 0.002, tolerance * 0.05)`. This is a one-way cage-to-source bound, not a bidirectional Hausdorff distance. Full source-triangle coverage is checked separately. The six `axisSupportGaps`, ordered -X, +X, -Y, +Y, -Z, +Z, compare source and boundary coordinate extrema: source minimum minus cage minimum on a negative axis, cage maximum minus source maximum on a positive axis. They exclude particle collision radius. They describe rest-geometry support offsets; near-zero -Y offset does not establish deformed settling, local belly contact, or runtime contact quality.

This is a bounded profile, not a general-purpose tetrahedral mesher. The original seal is preserved; the already prepared star-shaped source variant rounds the deep fin roots and tail, and the support-plane optimization does not alter it. The user requested configurable budgets: the seal defaults to a maximum of 30 controls, while the current compiler capacity allows up to 255 controls plus one root bone. The budget includes the center and mandatory insertions, is reflected and persisted, and is distinct from the four influences per displayed vertex; a valid candidate may use fewer than the maximum. The low-budget extension permits seven points (six shell points plus center), with additional room required for authored insertions. General quality defaults remain 0.16 m cage-to-display distance and 85% excess volume. The seal demonstration recipe tightens these acceptance limits to 0.12 m and 50% without changing the source, center, two mandatory points or 30-point budget. Thresholds are acceptance limits, not achieved measurements; actual volume, sampled distance, certified bound and support offsets are reported separately. The coarse collision proxy must not be described as the earlier 4 cm fit.

User points are inserted exactly by conforming local subdivision, including shared-face/edge handling. Automatically generated points are deterministic and bounded. Budget and quality are explicit; constrained points are never silently moved or snapped to another point. Thin parts, degenerate insertions or inadequate budgets produce diagnostics and leave the previous binding intact. Unsupported self-intersecting inputs fail explicitly.

Every displayed vertex is assigned to a containing valid tetrahedron. Barycentric weights must be finite, nonnegative within a documented numerical tolerance, sum to one, and have at most four positive entries. Out-of-cage vertices fail; no global nearest-four fallback. Each control point maps to a stable deformation bone beneath the root. Initial bone/inverse-bind transforms reproduce the rest mesh. No animation-child weight splitting is used.

### Supplied center fan and displacement binding

Recipe version two adds the explicit `SuppliedCenterFan` mode alongside the unchanged default `AutoFit`. In supplied mode the existing ordered `controls` array describes every physical control; `centerIndex` identifies its interior point, and `tetrahedra` supplies the complete fixed connectivity. Each tetrahedron must contain that center. The generator derives edges and boundary faces without inserting controls, filling the budget, reordering controls or fitting/scaling the collision cage. `fillControlBudget` is rejected for this mode. The existing Authoring target owns both paths; there is no additional importer, module, target or loading entry.

The supplied path accepts a closed connected display shell independently of its visibility kernel, but deliberately restricts its supplied cage to a convex, consistently oriented, closed degree-one center fan. Stored-precision validation rejects out-of-range or duplicate indices, duplicate or inverted tetrahedra, same-sided shared faces, open/disconnected boundaries, unused controls, an exterior center, non-convex boundary, or insufficient tetrahedron quality. Every embedded source corner must satisfy every outward cage half-space; convexity then establishes complete embedded-triangle coverage. Cancellation and failure preserve the previous complete output. This is a restricted supplied-cage contract, not a general tetrahedral-soup validation claim.

`bindingPositionScale` defaults to one and is applied only to the baked model-space binding query `q = scale * P`. Supplied bindings store at most four normalized nonnegative tetrahedral barycentrics satisfying `sum(w_i * B_i) = q`. Original display position `P`, physical control position `B_i`, reference bone transform and inverse bind remain unchanged. Translation-only deformation therefore evaluates `P' = P + sum(w_i * (x_i - B_i))`; at rest it reproduces the complete original display mesh even when `q != P`. The original animal fixture explicitly uses scale 0.7 with its saved 15-control/24-tetrahedron/50-edge cage and sixteen bones, including root. It does not expand the physical cage by the inverse scale and does not copy the later animation-child weight splitting.

Attachments retain the existing single-control default and add a constant `BindingAnchor` mode. That mode obtains one four-weight tuple at the scaled model-space anchor and applies the same tuple to every vertex of its primitive. Eye and pupil primitives can share an anchor and move together without changing their shape. Body ears and limbs already connected to the source shell remain part of its four-weight displacement field; this does not add independent ear animation.

Coverage diagnostics explicitly distinguish binding-space coverage from display-space coverage. Binding-position reconstruction error is reported separately from rest skinning error. Source volume, cage volume/excess, cage-to-display distance certificate and signed axis support offsets continue to measure unscaled physical/display geometry; they do not measure the contracted embedding mesh. A supplied cage can have negative signed volume excess without invalidating its separate binding-space coverage. Configured quality thresholds remain explicit and the existing automatic-fit defaults are unchanged.

Recipe and product version two persist `normalPolicy`, with `TetGradient` as the default and `StandardSkinning` explicitly selected for displacement binding and constant-anchor accessories. Standard skinning publishes the completed control transforms and an empty custom normal palette, allowing the existing animation/render path to use ordinary inverse-bind skin normals. It still rejects invalid physical tetrahedral deformation. The reference translation-only skin preserves its stored normals under these control translations. A custom gradient field for displaced binding would require `J = I + (F-I) * scale`, while constant-anchor attachments have `J = I`; the current per-control gradient palette is not presented as that implementation. Version-one recipes and products remain readable with the original gradient default; new mode/policy values are range-checked before conversion, and the exclusive END sentinels are never accepted.

Version-two recipes also preserve an optional `materialSlots` UUID table. The editor and builder pass it through the existing consumer-owned mesh binding/compiler interface, preserving primitive material indices and the original geometry, normals, UVs and linear vertex colors. Mesh products retain their material references and dependencies; recipe build dependencies retain those referenced products. An empty table preserves the prior behavior. No material parameters are hidden in vertex attributes to replace missing slots.

Mandatory validation: source validity; preserved mandatory point identity/position/mode; deterministic cage topology; positive rest volumes and minimum shape quality; no duplicate/invalid edges or faces; complete skin coverage; allowed bone budget; normalized weights; stable product layout identity. Zero-weight entries must not accidentally erase geometric tetrahedron identity needed by shading diagnostics.

## D4 Source ownership and cook

Save one versioned softbody-rig recipe as the authoring source. It references the original mesh source and stable submesh identity, and stores control points, attachment policy, generator parameters and version. It does not overwrite imported FBX/glTF or edit only cooked buffers.

The builder loads source geometry through the registered mesh compiler service, runs the same Authoring algorithm used by the editor, and requests Mesh/Skin/Skeleton products through that service. Product construction returns any vertex remapping needed to retain binding identity. The builder adds SoftBody topology/binding data, allocates stable generated child keys under one source owner, and invokes checked SaveProducts once for the complete candidate. Existing flat product storage remains; do not introduce obsolete group-directory transactions. Failed generation/build never replaces a running complete skeletal candidate.

Real scene cooking requires static component and subsystem persistence without loading runtime/adaptor modules. ComponentFactory accepts a metadata-owned mapping from component identity to its reflected persistent data type, independently of the live component factory. WorldSubSystemRegistry similarly separates persistent config schema from a session's runtime factory. Animation component/subsystem data belongs to Animation.GraphAssets and softbody component data to SoftBody.Assets; runtime modules reflect only their live component classes and install runtime services. Cook validation accepts static schemas, while instantiation still requires the real runtime factories. Duplicate or conflicting schema registration fails and never replaces an existing owner.

Existing SaveProducts pre-encodes the batch but can invalidate disk products if a later atomic file replacement fails; it does not restore all old disk products. This change retains that contract and reports a recook-required failure. Keeping a live complete resource candidate is distinct from retaining the previous disk products. No full disk rollback claim is made.

Recipe save, cook completion and runtime candidate activation are distinct states. Diagnostics must identify which failed. Source deletion/revision changes, stale requests and closed documents cannot publish into a different owner or overwrite a later document revision.

## D5 Editor extension workflow

AssetGeneratorRegistry registers stable generator ID, supported input type/capabilities, label, reflected settings type and request factory. Registration rejects duplicate IDs and unregisters by owner. Requests have immutable input, cancellation, progress, explicit status and owned results; their lifetime does not depend on the window or a borrowed source pointer.

Mesh document exposes control-point creation/selection/movement/removal, fixed/kinematic mode, cage/bone/weight overlays and generation preview. Required actions are registered in EditorActionRegistry and shown through standard ToolBar/MenuBar. Settings use ReflectedFormView and per-document CommandService. Mesh document never branches on a particular SoftBody generator class.

The Mesh document displays the selected cooked mesh in an Aurora asset preview session with its original material slots. A skeletal product uses its matching Skin and Skeleton in reference pose. A saved binding restores its bones and cage without adding an undo entry. The editor prepares material shader programs on a worker and keeps servicing viewport input while the programs are pending. Weight mode overlays a bounded, depth-tested image computed from every indexed triangle and its interpolated vertex weights on the same view.

Mesh and character previews share the static mesh editor's initial orbit direction in Unreal Engine 5.8. Converting UE's thumbnail rotation to the imported rabbit's Y-up coordinates gives a Sky camera yaw of −22.5° and pitch of −11.25°. The preview maintains a horizontal field of view of 90° on resize. Alt plus left, middle or right drag orbits, pans or dollies. The wheel zooms and F fits the subject bounds while preserving the viewing direction. Plain left drag remains available for editing control points. These gestures follow [Unreal's viewport controls](https://dev.epicgames.com/documentation/en-us/unreal-engine/viewport-controls-in-unreal-engine).

The preview ground sits at the bottom of the subject's rest bounds and is excluded from camera framing. Previews can supply stable bounds, including effect bounds for a future particle editor. The renderer owns the stage independently of the caller's World. Weight overlays, picking, and bones use the same camera and viewport as the material pass. The ground follows [Unreal's asset preview scene](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Editor/AdvancedPreviewScene/FPreviewSceneProfile).

Very small compliance and quality values opt into scientific formatting through the existing reflection editor hint. The generic number editor preserves enough significant digits for editing round trips; no SoftBody-specific form or field renderer is introduced.

One-click Generate performs the pipeline from current mesh plus specified controls. On success a complete binding candidate is applied as one undoable command; Undo/Redo restores the full coherent set. A settings/source/control-point change invalidates stale results. Cancel/close drains owned tasks, and failures preserve the previous candidate. Save persists the recipe and requests cook; status distinguishes preview, unsaved, cooking, ready and failure.

## D6 Presentation and shading

Keep existing four-influence Aurora rendering and independent Mesh/Skin/Skeleton products. SoftBody publishes a completed fixed-step control sample, which is interpolated once and converted into a bone contribution. AnimationWorldHost combines it with base pose through an interface; SoftBody does not replace the global ISkeletalPoseSource.

Pure translation bones reproduce tetrahedral positional embedding, but their ordinary inverse-transpose matrices do not express the deformed surface normal. The initial shading plan computes a rest/deformed neighborhood gradient per control point and publishes an explicit normal-deformation contribution, composed with the animation normal transform. Existing Aurora palette preparation consumes the validated contribution. This is a smooth control-point approximation; affine compression/rotation fixtures must match analytic normal directions and nonuniform deformation must be visually inspected. Do not claim correct shading solely from position tests.

Root, points, bounds and shading use the same interpolated time. Material and shadow passes agree on the four-weight positions. Epoch, instance generation, skeleton layout and pose revision guard complete publication. Invalid new data retains a previous valid candidate with an explicit diagnostic.

The existing Mesh-to-render bridge maps asset UV1 through UV4 to canonical shader TEXCOORD channels 0 through 3. The asset enum already identifies the channel, so these attributes require semanticIndex zero; ambiguous nonzero indices fail explicitly. Asset serialization and VertexSemanticName remain unchanged.

## D3: Device benchmark extension

The user requests Release measurements for exact 30/25/20/15/10-control rigs: first two soft bodies against each other or one soft body against static/kinematic obstacles, then ten animals. Dynamic rigid two-way reaction is outside this extension. Existing targets and module load names are retained. Physics-owned `ISoftBodyWorldControl` and owned diagnostics are consumed by the external demo launcher; implementation stays in the existing SoftBody World adaptor and CPU solver targets. The existing World module registers/revokes the control service in Init/Shutdown.

### Batch ownership and supported contact

One private coordinator per validated World/physics owner holds weak component memberships; the native physics listener owns the coordinator, and each step temporarily acquires live component ownership. Stable actor UUIDs determine batch order. Before the one existing rigid update, the coordinator samples roots. Afterwards it preflights publication identities and runs one CPU `StepBatch`. All bodies are predicted in scratch storage, then internal XPBD, bidirectional vertex/triangle soft contact and rigid contact are projected. Signed closed-tetrahedron containment identifies interior points. Soft corrections and contact friction are distributed through inverse masses and triangle barycentrics; contact multipliers accumulate across iterations at the same step size. All candidate states validate before any snapshot is committed. Publication after commit is an owned move and introduces no fallible validation stage.

The initial soft-soft implementation supports discrete closed-cage surface contacts, not soft CCD, edge-edge contacts or self collision. Final surface crossings without supported containment/contact fail explicitly. Strong failure preservation is retained for the entire batch. A failed attempt is diagnostic data, never a successful low-cost frame. Closing the World, removing the last member or shutting down the module revokes borrowed services and contributions without a component/coordinator ownership cycle.

### Exact-count rigs and quality

`fillControlBudget` defaults false for old recipes. Exact mode inserts a shared stored-precision midpoint on a feasible longest boundary edge and conformingly splits incident cells before the normal complete validation chain. Small shell budgets use an octahedral seed; larger budgets retain the existing seed/support candidates. No isolated padding points are added. Infeasible exact counts or quality failures preserve the prior result.

The performance-only recipes retain the original 10,336-vertex / 20,480-triangle body, exact center and two authored Dynamic controls, with all controls Dynamic and four influences per displayed vertex. They explicitly allow coarser proxies than the production recipe; lower counts are not equal-quality alternatives. Total mass is normalized to 3 kg (`particleMass=3/N`), and follow compliance scales as `0.02*N/30`, preserving the mass/compliance product. This does not make discretized edge/volume stiffness or cage geometry identical. Radius remains 5 mm and four internal iterations are used. Every report must include actual topology and proxy distance/volume errors.

### Measurement and deployment

An optional external JSON config enables the demo-only benchmark session. Normal launch reads no solver clocks. The fixture reuses cooked World/Mesh/Skin/Skeleton/SoftBody products and the production interfaces; no runtime import or alternate physics implementation is bundled. Android packaging uses the existing project/export/cook pipeline, ARM64 and the actual CMake Release configuration, rather than inferring optimization from an APK directory name. Custom material variants enumerate SKINNED, SHADOWS and IBL combinations required by runtime feature selection. Test signing is separate from production signing.

Each measured fixed step records counts, active contacts, failures and elapsed buckets (prediction, internal XPBD, rigid query/projection, soft broadphase/narrowphase/projection, final validation). Profiling defaults off; enabled World history is bounded at 4096 owned entries and expired cursors fail explicitly. `totalNs` contains bookkeeping and is not added to its component buckets. These elapsed timers are not thread CPU time. Separate application-loop process CPU time and wall time distinguish CPU work from waits; neither proves GPU frame rate. Native rigid-step diagnostics are also recorded separately.

Android's application loop can run many times without advancing physics. The benchmark therefore retains raw records only for physics-bearing loops, with independent fixed-step capacity, and exports bounded histograms for every zero-step/physics-bearing loop. Counts, sums, minima, maxima and means remain exact; histogram percentile upper bounds have relative error at most 1/64. Loop CPU intervals cover `Application::Loop`, excluding benchmark collection/serialization outside it. Busy-loop work and instrumentation perturbation must not be labelled physics cost or display FPS.

Device testing also exposed an animation-startup race: a valid Pending instance has identity before its Skeleton version becomes available. Animation Query validates identity first and compares the Skeleton only for Ready results. The scene bridge defers first publication or retains the previous complete resource/pose/transform tuple while Pending, without converting normal asynchronous readiness into a fatal renderer error. Genuine identity/epoch errors and Ready rig mismatches remain errors.

The ten-body scene exceeds the existing frame-lease default of 256 descriptor sets: ten complete 25-part animals with a main and shadow pass need approximately 500 distinct skinning batch bindings. The underlying RHI allocation limits already exist, but the Renderer did not expose them. `RendererInitInfo` now carries three bounded descriptor counts, passed through the existing Runtime into the frame context. Existing Aurora launcher arguments configure them explicitly; other hosts keep their defaults. The benchmark launcher requests 8192 resource descriptors, 2048 samplers and 4096 sets. Material draws currently create separate native samplers, so a shared atlas does not imply shared sampler bindings. For the current single-view/single-shadow fixture, a conservative no-sharing bound is 4034 resources, 1009 samplers and 1513 sets.
